## Step-by-step

### 1. Read the template package to find out what it actually provides — JUDGEMENT

`greta.pkgdown`'s README is good and states the contract, but I still had to
read `inst/pkgdown/BS5/` to know what *not* to copy. The key fact, which is
easy to get wrong, is that a consumer needs **almost nothing** locally:

| Asset | Comes from | Consumer needs to do |
|---|---|---|
| bslib theme (purple, Roboto, code-bg) | template `_pkgdown.yml` | nothing |
| `extra.scss` | template `inst/pkgdown/BS5/extra.scss` | nothing |
| navbar wordmark image | template `inst/pkgdown/BS5/assets/name_icon_on_white.png` | nothing |
| `templates/navbar.html` override | template | nothing |
| `right:` navbar (search / forum / github) | template `_pkgdown.yml` | nothing |
| favicons | **nobody** | copy by hand |
| reference index | **nobody** | write by hand |
| `left:` navbar | **nobody** | write by hand |
| home title/description | **nobody** | write by hand |

The naive move — copying greta's whole `pkgdown/` directory across — would have
duplicated `extra.scss`, `assets/`, and `templates/` into greta.dynamics and
silently defeated the point of having a shared template. Verified the assets
really are inherited by reading `pkgdown:::copy_assets`, which copies
`inst/pkgdown/BS<version>/assets` from `template$package`. A helper should
never copy those three.

### 2. Set the template — MECHANICAL

```yaml
template:
  package: greta.pkgdown
  bootstrap: 5
```

`bootstrap: 5` is still required in the consumer's own file even though the
template is BS5-only: pkgdown resolves `pkg$bs_version` from the consumer
config *before* it looks in the template package, and that value is what
selects the `BS5/` subdirectory. Dropping it silently gives you a BS3 site with
none of the theme. Non-obvious, worth a comment or a hard check.

### 3. Favicons — MECHANICAL COPY, but nothing automates it

pkgdown reads favicons from `<pkg>/pkgdown/favicon/` (`pkgdown:::copy_favicons`)
and there is no mechanism for a template package to supply them. So I copied
greta's set verbatim:

```
cp -R greta/pkgdown/favicon greta.dynamics/pkgdown/
```

Two things made this safe, and a helper should verify both rather than assume:

- greta's `site.webmanifest` has **empty** `"name"` and `"short_name"` fields,
  so it is package-neutral and needs no editing after copying. If someone ever
  fills those in for greta, blind copying starts branding every extension
  package as "greta".
- the filenames greta ships (`favicon-96x96.png`, `favicon.ico`, `favicon.svg`,
  `apple-touch-icon.png`, `web-app-manifest-{192,512}.png`) are exactly the
  names pkgdown 2.2.0's `BS5/templates/head.html` looks for. This is because
  they were generated by RealFaviconGenerator, whose output happens to match.
  A hand-rolled set with different names would produce a site with no favicon
  and no warning.

**This is the single strongest argument for a `use_greta_pkgdown()` helper**:
the favicon set should be shipped *inside* greta.pkgdown (e.g.
`inst/favicon/`) and stamped into the consumer's `pkgdown/favicon/` by the
helper, so the greta family shares one icon set with one place to update it.

### 4. `home:` block — JUDGEMENT, with a trap

I set:

```yaml
home:
  sidebar: false
  title: ...
  description: ...
```

`title` and `description` are pure judgement — they are the `<title>` and meta
description of the landing page and have to be written per package.

`sidebar: false` is the trap. The shared `extra.scss` contains:

```scss
.template-home {
  aside { display: none; }
  main.col-md-9 { flex: 0 0 100%; max-width: 100%; }
}
```

That rule is in the "SHARED CHROME"… actually it is under the file's
"HOME-PAGE SCAFFOLDING (opt-in)" heading, but unlike the `#head` / `#bullets` /
`#panel1` rules it is **not** gated on any id the consumer must supply — it
fires on `.template-home`, which pkgdown puts on every home page. So any
package that adopts the template and does *not* set `home: sidebar: false`
gets its sidebar (dev links, license, citation, authors) rendered into the HTML
and then hidden by CSS. The content is generated, paid for, and invisible.

Two possible fixes, both for greta.pkgdown rather than for consumers:

- (preferred) move the `.template-home` block behind an opt-in id so it only
  applies to greta-style hero home pages; or
- treat `home: sidebar: false` as part of the template contract, document it,
  and have `use_greta_pkgdown()` write it in and warn if a consumer removes it.

Either way a helper should not leave this to chance.

### 5. Navbar `left:` — JUDGEMENT

Only `left:` is the consumer's job; `right:` (search, forum, github) is
inherited. I used `[reference, articles, news]` and followed greta's
lower-case, informal labelling ("docs", "examples") rather than pkgdown's
defaults ("Reference", "Articles", "Changelog"). That house style is not
written down anywhere — I inferred it from greta's `_pkgdown.yml`. If it is
intended to be the family style it belongs in the template's shared
`_pkgdown.yml` as default `reference:` / `articles:` component overrides, and
then no consumer has to know about it.

The `articles` dropdown hrefs (`articles/iterate-matrix-example.html`) had to
be derived by hand from vignette filenames. Mechanical, but a helper can do it
by globbing `vignettes/*.Rmd` — the *labels* still need a human, since the
vignette titles here are unhelpful (one is literally
`title: "iterate-matrix-example"`).

### 6. Reference index — JUDGEMENT

pkgdown errors if the index does not cover every topic, so this cannot be
skipped once you add a `reference:` block at all. Grouping the five topics
(three iteration functions, `ode_solve`, the package doc) into three sections
with descriptions is editorial work.

One mechanical gotcha: the package-level topic must be listed by its **alias**
`greta.dynamics-package`, not by the `\name{}` `greta.dynamics`. Had to open
`man/greta.dynamics.Rd` to find that out.

A helper can generate a valid *stub* — one section per topic, or a single
"All functions" section — that builds cleanly and is obviously a placeholder
for the maintainer to reorganise. That is much better than nothing, because the
all-topics-must-be-covered rule means a half-written index is a build error.

### 7. `development: mode: auto` — JUDGEMENT (mild)

Copied from greta. Effect: the navbar version badge is styled by release state
(here `text-muted` / "Released version" for 0.2.3) and dev versions build to
`docs/dev/`. Sensible family default; safe for a helper to write in, but it
does change where CI publishes for dev versions, so it should be mentioned, not
silent.

### 8. Things that needed **no** change — but a helper must still check

All four were already correct in greta.dynamics. None are guaranteed in
general, and three of them fail silently:

- `url:` in `_pkgdown.yml` — required for the github navbar item to be derived
  and for `build_site_github_pages`.
- `URL:` in `DESCRIPTION` including the pkgdown URL — CRAN-visible.
- `.Rbuildignore`: needs `^_pkgdown\.yml$`, `^pkgdown$`, `^docs$`. Missing
  entries here produce R CMD check NOTEs, which for a package mid-CRAN-
  resubmission is exactly the wrong surprise.
- `.gitignore`: needs `docs`.

### 9. Smoke test — see the CI section, this is the interesting part

```r
pkgdown::build_reference_index(".")   # also runs init_site: assets + favicons
pkgdown::build_home(".")
```

Both succeeded. Verified in `docs/index.html`:

- `<img ... class="navbar-logo" alt="greta">` — wordmark override active
- `docs/name_icon_on_white.png` present — inherited from the template package
- `A379CC` compiled into `deps/bootstrap-5.3.8/bootstrap.min.css` — theme active
- `deps/Roboto-0.4.10/`, `deps/Roboto_Mono-0.4.10/` — fonts active
- `fa-comments` (forum) and `fa-github` present — shared `right:` navbar active
- favicon `<link>`s emitted, all seven files copied to `docs/`
- version badge renders `0.2.3` with tooltip "Released version"

**Upstream bug spotted, not ours**: pkgdown 2.2.0's `BS5/templates/head.html`
line 9 uses typographic quotes —
`<link rel="icon" type=”image/svg+xml” href=...>` — so the SVG favicon link is
malformed in the output of *every* pkgdown 2.2.0 site, not just this one.
Harmless (browsers fall back to the PNG/ICO) and out of scope, but worth an
upstream issue and worth not re-debugging next time.

## Packages whose vignettes are too expensive to build

greta.dynamics' two vignettes execute TensorFlow and take minutes each. This
constrains the workflow in ways that are worth designing around, because it
applies to most of the greta family, not just this package.

**Local iteration.** Never `build_site()`. The theme-affecting stages are
`init_site()` (assets, favicons, compiled SCSS), `build_home()`, and
`build_reference_index()`; all are fast and all are independent of vignettes.
`build_reference_index()` implicitly runs `init_site()`, so those two calls
cover everything a theme change can break. A `use_greta_pkgdown()` helper
should *print this recipe* rather than telling the user to run `build_site()`,
and it is the obvious basis for a `greta_pkgdown_preview()` companion.

**What you therefore cannot check locally.** Article pages are never rendered,
so the `articles:` index and the navbar dropdown hrefs are unverified — a typo
in `articles/ode-solve-example.html` is a dead link that no local check
catches. A helper that derives those hrefs from `vignettes/*.Rmd` removes the
only class of error this workflow is blind to, which makes the derivation more
valuable here than it would be in a normal package.

**CI.** greta.dynamics' `.github/workflows/pkgdown.yaml` is the old r-lib
actions v1 template using `deploy_to_branch`, which builds the full site,
vignettes included. On a runner with no GPU and a fresh conda/TF install that
is slow at best and a failure at worst. greta.pkgdown's own workflow is the
current v2 template. Migrating greta.dynamics to it is a sensible follow-up but
is **outside the lane I was given** (`.github/` was not mine to touch), so I
left it. Flagging it as the next piece of work: the v2 workflow also does
`extra-packages: any::pkgdown, local::.` with `needs: website`, which is what
makes the `Config/Needs/website` line below actually take effect.

## ⚠️ Required follow-up I deliberately did not do

`DESCRIPTION` needs:

```
Config/Needs/website: greta-dev/greta.pkgdown
```

Without it, `setup-r-dependencies` will not install greta.pkgdown on the runner
and **the pkgdown CI job will fail**, because `template: package:` names a
package that isn't there. greta.pkgdown's own README documents this line.

I did not add it because my instructions limited me to `DESCRIPTION`'s `URL:`
field, and another agent is editing `DESCRIPTION` concurrently — a same-file
edit risked clobbering their work. It is a one-line append and should be made
before the pkgdown workflow next runs.

(Note that greta itself does *not* have this line, because greta inlines the
theme in `pkgdown/_pkgdown.yml` rather than consuming the template package.
greta is the design reference for *what the site looks like*, but it is not an
example of a template *consumer*. The only real consumer today is
greta.pkgdown's own site. Worth knowing before treating greta as the model.)

## Specification for `use_greta_pkgdown()`

### Do automatically, no questions

1. Create/patch `_pkgdown.yml`:
   - `template: {package: greta.pkgdown, bootstrap: 5}` — both keys; error
     loudly if `bootstrap: 5` is absent, since its absence is silent.
   - `url:` from `DESCRIPTION`'s `URL:`, or derived as
     `https://greta-dev.github.io/<pkg>/`.
   - `development: mode: auto`.
   - `home: sidebar: false` (until the shared SCSS stops requiring it).
   - preserve any existing user content; never clobber a hand-written
     `reference:` or `navbar:`.
2. Copy the shared favicon set into `pkgdown/favicon/` — **from greta.pkgdown's
   own `inst/`, which means adding it there first**. Leave an existing
   `pkgdown/favicon/` alone.
3. Ensure `.Rbuildignore` has `^_pkgdown\.yml$`, `^pkgdown$`, `^docs$`
   (`usethis::use_build_ignore()`).
4. Ensure `.gitignore` has `docs`.
5. Ensure `DESCRIPTION` has `Config/Needs/website: greta-dev/greta.pkgdown`.
6. Ensure `DESCRIPTION`'s `URL:` contains the pkgdown URL.
7. Offer to install/refresh the r-lib actions **v2** pkgdown workflow, warning
   when the existing one is the v1 `deploy_to_branch` template.

### Generate as a stub for the maintainer to edit

8. `reference:` — one group containing every topic, resolving package-level doc
   to its `-package` alias, with a `# TODO: organise` marker. A stub is
   necessary, not merely nice, because pkgdown hard-errors on uncovered topics.
9. `articles:` and the navbar `articles` dropdown — hrefs globbed from
   `vignettes/*.Rmd` (this is the one thing local smoke-testing cannot verify),
   labels defaulting to the vignette title with a TODO where the title is just
   the filename.
10. `navbar: structure: left: [reference, articles, news]` with the house-style
    lower-case labels — or better, move those labels into greta.pkgdown's
    shared `_pkgdown.yml` so consumers inherit them and this step disappears.
11. `home: title:` / `description:` — placeholders seeded from `DESCRIPTION`'s
    `Title` and `Description`.

### Never do

12. Do not copy `extra.scss`, `assets/`, or `templates/` from greta or from the
    template package into the consumer. They are inherited; copying them
    forks the theme.

### Print at the end

13. The vignette-safe smoke test:
    `pkgdown::build_reference_index(".")` then `pkgdown::build_home(".")`,
    with an explicit "do not run `build_site()` if your vignettes execute
    TensorFlow".

### Changes to greta.pkgdown that would shrink this function

- ship the favicon set in `inst/`
- move the house-style navbar labels into the shared `_pkgdown.yml`
- gate the `.template-home` sidebar-hiding rule on an opt-in id, or document
  `home: sidebar: false` as part of the contract
- state in the README that `bootstrap: 5` must be repeated in the consumer
