# Issue #504 — `sd()` on a greta array returns a base numeric

## Approach

`sd()` in base R is a plain function (not an S3 generic), so greta cannot
dispatch on it and `sd(x)` falls through to `stats::sd()`, which coerces the
greta array to a number. PR
[#506](https://github.com/greta-dev/greta/pull/506) already implements the fix:
it promotes `sd` to a generic, adds `sd.default`/`sd.greta_array`, a `tf_sd`
backend, and registers `sd` in the `apply()`/`tapply()` `FUN` menus.

rebase onto `main`, drop the noise, fix a small doc typo, add a test.**

## Acceptance test

Add to `tests/testthat/test_functions.R`, beside the `mean()`/`var()` tests:

```r
test_that("sd() on a greta array returns a greta array", {
  x <- normal(0, 1, dim = 10)
  s <- sd(x)
  expect_s3_class(s, "greta_array")
  expect_equal(dim(s), c(1L, 1L))
})

test_that("sd.default still works on plain numerics", {
  expect_equal(sd(c(1, 2, 3)), stats::sd(c(1, 2, 3)))
})

test_that("sd() matches stats::sd numerically", {
  x <- as_data(c(1, 3, 5, 7))
  expect_equal(as.numeric(calculate(sd(x))[[1]]), stats::sd(c(1, 3, 5, 7)))
})
```

## Correction: `var()` is broken too, and must ship with `sd()`

The issue says `var()` returns a greta array. It does not. `var(x)` returns a
base matrix containing `NA` - the same class of failure as `sd()`, and for the
same reason: `stats::var` is not generic either. So there is no working
`var()` fallback to point users at in the meantime, and a fix that promotes
only `sd` will have the issue reopened immediately.

Promote **both**. The "very low effort" rating in this document holds for
`sd` alone; the real scope is twice that. Register both in the `apply()` and
`tapply()` `FUN` menus at the same time - `apply(z, 2, "sd")` currently errors
with a menu that omits it.
